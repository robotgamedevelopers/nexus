# models: the TLA+ specifications of nexus

Every state machine in nexus has a TLA+ module here (`Overlay.tla`, when the overlay shows and hides, among them). TLC checks each module on a small instance, with reversed witnesses, and the code is bound to the module: the code's own random walk writes traces, and TLC checks that each trace is a behaviour of the module.

This file covers the window's model. The server's durable state has its own directory: `store/` (its README), the layout of the journal under `src/store/`, and the store's lock with the server's start-up order (`StoreLock.tla`). The server's installed builds have
`placement/` (its README): placing a build, switching current and previous in one rename, and pruning. Replacing the running server with a placed build has `handover/` (its README): draining, starting, rolling back when a build fails to serve, and resuming from durable state on disk after any cut. Keeping the placed service running across boots, drain handovers, intentional stops, and post-start build failures has `supervision/` (its README). Moving a pre-`~/.nexus/server` layout once under an OS lock and checking the store's format against rollback has `migration/` (its README). Binding all five takeover layers together end to end across upgrades, drains, cuts, post-start crashes, format bumps, and rollbacks has `takeover/` (its README).

## What is modelled

`Window.tla` is the state the window owns, `nexus::Model` in `src/model.h`:

- `ais`: the AI tabs that stand, by id (`Tab::id` in the code), each with its AI. The model is built with a list (its ids are their places in it, from 0); `AddAI` and `RemoveAI` add and remove tabs as the server's list of AIs changes (`sync::applyAIs`). An id never changes and is never reused: an AI that comes back gets a new tab with a new id;
- `order`: the tabs' order, each position's tab id. An AI tab's id is its AI's; a terminal tab's id is one handed out by `AddTerminal`. Positions count from 0, as in the code;
- `nextId`: the next id `AddTerminal` hands out. Ids only grow, so no id is ever used twice;
- `active`: the active tab's position, 0 when there are no tabs;
- `history`: the selection history, `Model::selection_history()`: the ids of the tabs selected, most recent last, each once, open tabs only. The tab active at the start is its first entry; select and add put their tab's id at its end, and close takes the closed tab's id out. Closing the active tab makes the last id left in it active, the tab selected before it, whatever its kind; with none left, the rule before it (the tab now at its position, or the last), and that tab's id is then the history (`ClosedHistory`), so the history always ends at the active tab. It is kept for the run only;
- `transcript`: each AI's entries, kinds `Person`, `AI`, `Notice`;
- `draft`: each AI's unsent text;
- `queue`: each AI's prompts held for later, oldest first. The queue is apart from the transcript: it mirrors the queue the server holds, and its oldest prompt leaves it only by `TakeQueued`, when the server delivered it (the window's mirror's call; `Link.tla` models the delivery).

Transcripts, drafts and queues are indexed by AI, so they go with the tab when it moves; operations take positions, as the code's do, and act on `At(i)`, the AI at position i. The actions are the model's operations, with the arguments a caller passes, in range and out of it: `SelectTab(i)`, `SetDraft(i, t)`, `Send(i)` (the draft becomes a `Person` entry at the end of the tab's transcript), `Queue(i)` (the draft goes to the end of the tab's queue), `TakeQueued(i)` (the oldest prompt of the tab's queue leaves it), `AppendEntry(i, e)`, `MoveTab(from, to)` (the tab at `from` ends at `to` and the tabs between shift by one; refused when the two positions lie in different zones), `AddTerminal` (a terminal tab at the end, made active), `CloseTab(i)` (removes the tab at i, only a terminal), `AddAI(f)` (an AI's tab, empty, with the next id, at the end of the AIs' zone; refused for an empty name or one a tab already has; the active tab stays active) and `RemoveAI(i)` (removes the AI's tab at i with its transcript, draft and queue; if it was active, the tab selected before it shows, by close's rule). `Spec` has neither AI action; `SpecAIsWith(Arrivals)` adds both, with the AIs `AddAI` is tried with. A refused operation changes no model state.

Each tab kind has a zone (`Zone`): the sprint tab 0, AIs 1, terminals 2. The order runs by zone, and a move stays inside its zone. The sprint tab is there when the constant `Sprint` is TRUE (the window's model always has it): it is made at the start in position 0 with id `SprintId` (N, the first after the AIs'), alone in zone 0, so nothing moves before it, it never moves, and close refuses it. A terminal and the sprint tab hold no transcript, draft or queue: send, queue, set_draft and append refuse them.

`MoveTab` carries the code's index arithmetic, not only its result: the order is `Moved` (the code's `std::rotate`) and `active` is `MovedIndex` (the code's three-way adjustment of `active_`). The properties then state what that arithmetic must give in terms of AIs: the same AI active, every AI kept once, the others in their relative order.

`last` is a history variable, not model state: the operation just performed, its arguments and the value it returned. The action properties are stated through it, and a code trace's return values are checked against it.

All-whitespace means every byte is an ASCII space, tab, newline, vertical tab, form feed or carriage return; the empty draft is all whitespace. The spec does not compute this: the constant `Blank` names the drafts that are all whitespace, and each instance lists them.

| `SelectMovesToEnd` | action | a select that returns true, and every add, puts its tab's id at the end of the history and takes it out of where it stood |
| `CloseForgets` | action | a close that returns true takes the closed tab's id out of the history, and nothing else; but a history so left empty with tabs open is the tab now active, alone |
| `RefusedChangesNothing` | action | an operation that returns false changes no model state (a refused move among them) |
| `TranscriptsOnlyGrow` | action | entries are only appended: existing entries never change, move or go |
| `QueuesOnlyGrow` | action | but for a take, queued prompts are only appended: they never change, move or go |
| `AIsFixed` | action | no operation but add_ai and remove_ai changes the AIs |
| `NamesOnce` | invariant | no two AI tabs hold AIs of one name |
| `AddAIExact` | action | add_ai returns true exactly for a name that is not empty and no tab holds; then that AI's tab, empty, stands at the end of the AIs' zone with the next id, the other tabs in their order, and the active tab stays active |
| `RemoveAIExact` | action | remove_ai returns true exactly for an AI's tab, and removes that tab and no other, the rest in their order |
| `AIOpsKeepOthers` | action | add_ai and remove_ai change no other AI's transcript, draft or queue |
| `RemoveForgets` | action | a remove_ai that returns true takes the tab's id out of the history, and nothing else (as `CloseForgets`) |
| `RemoveActiveRule` | action | after a remove_ai, the active tab stays active; if it was the one removed, close's rule (`CloseActiveRule`) |

### Instances

`MCWindow.tla` gives the constants values and bounds transcript and queue length (`MaxLen`, a state constraint). The drafts are `""`, `" "`, `" \t\n"` and `"hi"` (one witness adds `"yo"`, so that an order of queued prompts shows); the appended entries are an AI's reply, an empty notice and an all-whitespace `Person` entry (append takes any entry). The checked instances use fewer (`MCDrafts3`: `""`, `" "`, `"hi"`; on three tabs `MCAppendEntries3`: the reply only), because every order multiplies the states: the spec does not compute whitespace, so a second all-whitespace draft adds only states. Positions run to one past the last tab, for both of a move's. TLC tells states apart by the model variables alone (`VIEW ModelView`), which is sound because no action reads `last` and no property reads it unprimed.

Every order of the selection history is a state of its own, so the history multiplies the instances with many tabs. The times are the studio's in a login session; CI's runners take about four times as long.

## The binding: code traces checked against the spec

`tests/model/trace_walk.cpp` drives the real `nexus::Model` with a seeded random walk (`trace_walk <seed> <steps> <ais> [--no-sprint] [--ais-churn] [--faulty | --faulty-queue | --faulty-move | --faulty-queue-cap | --faulty-send-trim | --faulty-send-dedup | --faulty-close | --faulty-sprint-move | --faulty-sprint-close | --faulty-close-fallback | --faulty-remove-ai] <out.tla>`). The model starts with the sprint tab, as the window's does, unless `--no-sprint`. With `--ais-churn` the walk also calls `add_ai` (ada, bo, cy, dee with no model, and an empty name: `TraceArrivals`) and `remove_ai` at random positions, so AIs come, go and come back as new tabs. The random numbers come from the seed alone. Each step calls one operation (adding and closing terminals among them, at most three open), with positions in range and two past the last tab (a move draws both, so moves across zones are tried and refused), drafts that are empty, all whitespace (including tab, newline, vertical tab, carriage return and form feed), text with quotes and backslashes, and text with whitespace before, after and around it, and entries of every kind. Two kinds of step repeat the last accepted send or queue with the same text to the same tab (a `set_draft`, then the `send` or `queue`), so that equal sends follow each other and queues grow long; the walk prints the longest queue (dozens of prompts at 1000 steps). Every 25th step is followed by a `take_queued` at the same position, a step that draws no random number, so the other steps are as they were. The walk writes `WindowTraceData.tla`: the arguments' domains and `Trace`, one record per step, holding the operation, its arguments, the return value and the model's whole state after it: the order (each position's `Tab::id`), the selection history and, by position, each tab's kind, AI, draft, transcript and queue.

`WindowTrace.tla` instantiates `Window` with those domains. Each of its steps takes the `Window` action the record names, with the record's arguments, and the invariant `TraceMatches` requires the spec's state and return value to equal the code's: the order, the active position and the history equal, and the tab at each position holding the state of the AI the spec has there. A step whose arguments lie outside the spec's domains has no successor and TLC reports a deadlock. The property `WindowSpec` checks the whole behaviour against `Window`'s `Init` and `Next`, and every `Window` property is checked on the trace too.

Two churn traces run per commit: seed 10 with the sprint tab and three AIs, and seed 11 with no sprint tab and no AI at the start, 1000 steps each. `--faulty-remove-ai` (churn only) walks a subclass whose `remove_ai` leaves the removed tab's id in the history, which TLC rejects at the first removal. The binding is shown to fail, eleven times with it: `--faulty-close-fallback` walks a subclass whose `close_tab` of the active tab ignores the history and keeps the rule before it (rejected at the first close of an active tab where the two rules differ); `--faulty-sprint-move` walks a subclass whose `move_tab` takes the sprint tab among the AIs, `--faulty-sprint-close` one whose `close_tab` closes it; `--faulty` walks a test-only subclass whose `send` accepts a draft that is all whitespace but not empty, `--faulty-queue` one whose `queue` also puts the draft in the transcript, `--faulty-move` one whose `move_tab` leaves `active` at the old position, `--faulty-queue-cap` one whose queue drops its oldest prompt past four, `--faulty-send-trim` one whose `send` strips trailing spaces, `--faulty-send-dedup` one whose `send` of the text just sent appends nothing, and `--faulty-close` one whose `close_tab` also removes an AI's tab. TLC must report `TraceMatches` violated at the first step where each fault shows.

## TabLabel.tla: a terminal tab's label across ssh sessions

`TabLabel.tla` is `nexus::TabLabel` in `src/remote.h`: one terminal tab's label. Once a frame the window observes the terminal: the remote label of its foreground process (the fleet machine its ssh reaches, its host if not a fleet machine, or none when the foreground is not ssh), the program's title, and `late`, whether the frame comes after the tail of the last session to end (the code compares the frame's time with that end plus `kSessionTailSeconds`). Its state is the code's members: `remote`, `before` (the title at the last observation outside sessions and masks), `after` (the title a session left), `masking` and `tail`; `last` records the observation. `Label(t)` is the label drawn when the title is `t`.

| Property | Kind | What it says |
|---|---|---|
| `TypeOK` | invariant | every variable has its type |
| `TailMasks` | invariant | a tail is part of a mask |
| `SessionNamed` | invariant | while a session is seen, the label is its remote label, whatever the title |
| `TitleShows` | invariant | outside sessions and masks, the label is the title |
| `SessionNamedAtOnce` | action | an observation of a session names it at once |
| `EndRestores` | action | the observation that sees a session end gives back the label from before it, whatever title it left |
| `TailRestores` | action | in the session's tail the label stays the one from before, whatever title arrives |
| `MaskEnds` | action | past the tail, the first title other than the one the session left is shown: the label never sticks |
| `BeforeIsOwn` | action | the label to return to only ever changes to a title observed outside sessions and masks |
| `BeforeIsLatest` | action | and every such observation takes it |

`TabLabel.cfg` checks them on two remote labels and three titles (295 states). Its witnesses: `WLabelNoMask` (a session's end shows the title it left; `EndRestores`), `WLabelMaskSticks` (the mask never lifts; `MaskEnds`), `WLabelBeforeAtStart` (the label to return to is the title at a session's first observation, which ssh may already have set; `BeforeIsOwn`), `WLabelNoTail` (no tail, so a last title read after the process is seen gone shows; `TailRestores`).

`tests/model/label_walk.cpp` (`label_walk <seed> <steps> <remotes> [--faulty-before] <out.tla>`) drives the real `TabLabel` with a seeded walk on a made-up clock (a frame or a pause a step): sessions start, run, switch and end, titles change, and frames fall inside tails and after them. It writes `TabLabelTraceData.tla`: one record per observation with its arguments, the code's state after it and the label the code draws for every title. `TabLabelTrace.tla` takes `Observe` with each record's arguments and `TraceMatches` requires the spec's state and every label to equal the code's; every `TabLabel` property is checked on the trace. Four traces run (seeds 1 to 3 on two remotes, seed 4 on three), and `--faulty-before`, which feeds the code an unrecorded observation before each session's first (the code then takes the label to return to from a title ssh may have set), must be rejected with `TraceMatches` violated.

## TerminalWatch.tla: foreground-group synchronization between the poll and frame threads

`TerminalWatch.tla` models `src/terminal_watch.h` (used by `nexus::PraxTerminals` in `src/terminals.cpp`), which keeps one terminal's observed foreground process group in step between the background poll thread (every 250 ms) and the frame thread (which reads the group itself when the terminal's title changes, so `TabLabel` sees the foreground as of that title without waiting for the poll). Both threads run their system calls outside `mutex_`, and commit into `shared` (`[seq, group, remote]`, with `recheck`) under `mutex_`.

| Property | Kind | What it says |
|---|---|---|
| `TypeOK`, `SeqOrdered` | invariant | every variable has its type, and `seen.seq <= shared.seq` |
| `RemoteMatchesGroup` | invariant | every committed observation carries a real group and that group's remote label |
| `SeqMonotone` | action | sequence numbers never go backward |
| `FrameSeesTitleGroup` | action | a title-change commit immediately gives `seen` the foreground group and remote read for that title |
| `PollNeverClobbersFrame` | action | a background poll whose snapshot was overtaken by a frame commit never overwrites `shared` and asks for a recheck |
| `OverlapAsksRecheck` | action | a frame commit that overtakes a background commit between `FrameStart` and `FrameCommit` asks for a recheck |
| `SettlesToForeground` | temporal | once foreground and title changes stop, `seen` settles to the terminal's true foreground group and remote label, even across `G_sh -> G_ssh -> G_sh` ABA transitions within one poll window |

`TerminalWatch.cfg` checks every property across three groups (a shell and two ssh sessions), two foreground changes and two title changes. ## Link.tla: what nexus adds on top of mosh

`Link.tla` models the link between the windows and `nexus-server` (`src/sync`, `src/link`, `src/server`): what nexus puts on top of mosh's State Synchronization Protocol, not mosh. mosh is abstracted to the two things nexus relies on. Up, what reaches the server of a window's list is some range of it, which may repeat a range, come after a later one, or start past what the server has: `Deliver(c, first, last)` takes any range. Down, a window's receiver eventually holds the server's newest state, may skip states between, and never goes back to an older one (mosh numbers its states and keeps the newest): `Receive(c, j)` is window c receiving the server's j-th state, the same as before or a later one.

- Up: `acts[c]`, window c's actions, numbered from 1 (`sync::Actions`): a send, a queue or a stop naming a session id (held or not), a create for an AI copying no session or a given id, or an ensure for an AI; `applied[c]`, the server's `sync::Applier` for it; `done[c]`, a history variable, every number the server applied, in order. The Applier applies the numbers past `applied[c]` in a range, refuses one that starts past `applied[c] + 1`, and ignores one wholly applied.
- The server: `ses[i]`, the session with id i, its AI, or none (`NoSes`), over the ids 1 to `MaxSessions` (the hub's limit); `nextSid`, the next id the store mints, durable; `minted` and `skipped`, history variables: each id minted with the action that made it (the sessions of `Start`, there from before, by none), and each action applied that changed nothing. `tr[i]` and `q[i]`, each session's transcript and queue (`sync::Hub` over its store, durable); `op[i]`, its open entry, the AI's text still growing (`Hub::setOpen`, in memory only); `stops[i]`, a history variable, every stop applied naming the id, and whether it reached the responder (the drivers) or was refused because the server holds no such session. A send puts the prompt and a placeholder reply in the session's transcript, a queue the prompt in its queue, each only in a session the server holds; a stop changes no session. A create mints the next id for its AI unless the server is at its limit or the session it copies does not exist; an ensure does the same only when the AI has no session. The server's own steps: `Grow(i)`, in a session that has had something sent or queued, (an open entry is made, numbered, or grows), `Close(i)` (the open entry is closed into the transcript, all its text, and is gone), `Take(i)` (with no entry open, the queue's oldest prompt is delivered: it leaves the queue and is the person's entry in the transcript), `Restart` (the server starts again from its store, its sessions and its next id with it: every open entry is lost and its turn cut with a notice). `made` counts the open entries made, the grows and the restarts. Each change makes a new state in `snaps`: for each session held, its AI, its transcript's newest `W` entries from index `first` (`sync::tailOf`, by count; the byte budget is not modelled), then the open entry, which the tail does not count, so the newest closed entry always comes with it; and the whole queue.
- Down: `last[c]`, the state window c's receiver holds; `shown[c][f]`, the session AI f's tab shows (0 for none yet): the window's own choice, in its mirror (`Mirror::session`), the AI's first session (the lowest id) in the first state that holds one, kept from then on; `view[c][f]`, `vq[c][f]`, the tab's transcript and queue; `seen[c][f]`, its mirror: the transcript index it shows through; `live[c][f]`, the open entry the mirror holds apart from the transcript (`Mirror::open`). Receiving a state, the mirror appends a notice of how many entries left the tail before it saw them, then the closed entries it has not shown, stopping at the open entry, which it holds; and makes its queue the state's (the prompts the server took leave its head, `Model::take_queued`, and those queued since go at its end).

Entries are records: a prompt `[k |-> "P", text |-> <<c, n>>]` (action n of window c, sent, or queued and delivered), its reply `[k |-> "F", text |-> <<>>]`, the AI's grown text open `[k |-> "O", text |-> <<g, len>>]` and closed `[k |-> "G", text |-> <<g, len>>]` (the g-th open entry, of len pieces), the notice of a turn a restart cut, which lost open entry g, `[k |-> "X", text |-> <<g>>]`, a notice of m entries not shown `[k |-> "N", text |-> <<m>>]`.

Not modelled: mosh (sockets, crypto, fragments, timers, acknowledgements, its own correctness); the hub's limits on text and queues (a refused prompt becomes a notice in the transcript, which the mirror shows like any entry; the limit on sessions is `MaxSessions`); a session's harness, account, model and effort, and the actions that set them, which change no transcript or queue but for a refusal's notice (the hub's checks are unit-tested, by `hub_settings` and `hub_create_copies_settings`, and what a change does to the driver is `Supervisor.tla`'s); the turns themselves and what ends them (`Supervisor.tla`): here the server's own steps happen whenever their guards allow. So a restart cuts only a turn with an open entry; the code also cuts an open turn with no text yet, or whose text is all closed, and that notice is an entry the server appends like any other, which the properties on the transcript already cover. The binding stands a responder in for the drivers: the supervisor's take and stop are bound by `Supervisor.tla`'s trace check, while how `Drivers` turns its output into the hub's changes (the take first, then the effects, then the driver's state) is tested end to end by `ais_functional_queue`, `ais_functional_queue_unconfigured` and `ais_functional_stop`, not trace-checked.

How much is durable, and when (the decision behind `op`): the open entry is in memory only, and becomes a durable closed entry at its block's end (text-end, a tool line, the turn's done or cut, or the entry limit: one journal record per block, never one per delta). A restart loses at most the open block's text, and the restart's cut notice says the reply was cut; a closed entry is in the store once, and the mirror appends only closed entries, each index once.

## Supervisor.tla: a session's driver

`Supervisor.tla` models `src/server/supervisor.h`, the state machine `nexus-server` keeps per session: it starts the session's driver when a prompt waits, writes each prompt as the next turn, gathers the AI's text, stops a turn, and ends the driver (input closed, then TERM, then KILL, each after its grace period). The driver is the environment: any message of any kind, for the open turn or another, a line the server refuses, a pipe closing, an exit at any moment. A driver that reports `no-credential` (protocol rule 11) is ended once no turn is open, and no driver is started again until the person's next prompt. Deadlines are steps that may happen (no hello, no done after a stop, each grace while ending); a working turn has none. `Restart` is the server dying and starting again from what the store holds: the next turn number, the open turn, the last session id, the waiting prompts and the queue. `Shutdown` is the server stopping. The queue is the person's prompts held for later (Command-Enter), the hub's queue of the session; the waiting prompts are those a send left for the driver. `QueuePrompt` puts a prompt at the queue's end, and `Take`, after every event, moves the queue's oldest prompt to the waiting prompts once no turn is open and nothing waits, shown as the person's entry: one per turn, oldest first, each once. So a prompt queued with the AI idle goes at once, a sent prompt waiting goes before the queue, and a stop ends the turn and lets the next queued prompt go. Not modelled: the server also takes nothing while the AI has no driver configured (its drivers file lost it): the model's driver is always configured, and that guard only makes `Take` enabled less often, so every safety property still holds; `supervisor_unit_queue` and `ais_functional_queue_unconfigured` and `ais_functional_restart_unconfigured` test it. `Stop` ends what runs when it arrives: it writes one stop for the open turn, or, while the driver starts, cancels the turn about to begin (its prompt leaves the waiting prompts, never written, with a notice; the driver keeps starting for the next). One that finds the turn already stopping, or nothing running, changes nothing: no stop is kept for a later turn. `stops`, a history variable, records each stop written, and `asked` marks the step of the person's stop.

Invariants: `TypeOK`; `OneDriver` (at most one driver process, alive exactly when the phase says so); `OneTurn` (at most one turn open, only while a driver works on it); `TurnsIncrease` (a turn number is never reused, across driver and server restarts); `AtMostOnce` (each prompt is written to a driver at most once, ever); `WaitingSound` (a prompt waits only while the driver cannot take it, within the bound); `LimitHolds` (the failed-start count stays within its limit); `QueueSound` (the queue within its bound, each prompt in it once, and in it exactly while queued); `StopOnce` (at most one stop written per turn). Action properties: `StopForOpen` (a stop is written only for the open turn), `StopEndsWhatRuns` (a stop ends what runs when it arrives: the open turn, or while the driver starts the turn about to begin, its prompt cancelled and never written; finding the turn already stopping, or nothing running, it changes nothing), `NoLatchedStop` (a stop is written, or a turn cancelled, only in the step of the stop that found it running, so a stop that found nothing never touches a later turn), `TakesAtTurnEnd` (a queued prompt leaves the queue only at a turn's end, the oldest, one per turn, as the person's entry), `EffectsForOpen` (every entry of a turn is for the turn open before the step), `EndsAnsweredOrCut` (a turn ends by its done or by a cut with its notice), `TextKept` (gathered text goes into the session before the turn's closing notice), `StartsSound` (a driver starts only when not held back, and with `--resume` the last session id), `NoSendWithoutCredential` (no prompt is written to a driver that reported it has no credential), `WrittenWithSetting` (a prompt runs with the model and effort the session has when it is written: a change applies from the next turn), `SettingLeavesTurn` (a change of the model or effort never touches a turn in progress: no line written, no driver started, no turn opened or ended, no entry; an idle driver it must end is ended quietly), `NoSendOnOldAccount` (a prompt is written only to a driver started under the session's account as it is then), `AccountKeepsTurn` (a change of the account never ends a turn: the driver under the old account is ended once no turn is open, never counted as a failed start). Liveness: `Settles` (every prompt accepted is answered or cut, or waits while starting is held back or the server is stopping), under fairness for deadlines, the person's stop of a working turn (`StopWorking`: there is no deadline on one; a stop of a start is never assumed, so no prompt settles by being cancelled) and KILL.

A setting is a record of a model and an effort, each from `Models` or `Efforts` or `""` (the harness's default); `Accounts` are the accounts the person may choose besides the default, and `MaxSwitches` how many changes they make in all. A driver starts on the defaults, and `told` is what it has been told since: before a send, a `settings` line gives it each field where the session's differs, and it applies the line from that send on, a field left out staying as it is (`docs/driver-protocol.md`). That line cannot put a field back to the default, so a driver told a field the session has cleared is ended once no turn is open, like one under an old account, and the next starts on the defaults. Instances: `MCSupervisorSwitch.cfg`, the changes of model, effort and account, with two prompts, one failed start, no restart and one change (77,116 states, 45 s on four workers on an idle 16-thread Linux bench, no faster on eight); `MCSupervisor.cfg`, two prompts, one waiting, two failed starts, one restart, one session id (28,604 states, 16 s on eight workers on an idle 16-thread Linux bench); nightly, `MCSupervisorQueue.cfg`, three prompts, two waiting or queued, no restart (111,319 states, 33 s), `MCSupervisorWide.cfg`, three prompts (each sent or queued), three failed starts, two restarts, two session ids (1,117,970 states, 4 min 11 s on eight workers, so capped at 900 s), and `MCSupervisorSwitchWide.cfg`, `MCSupervisorSwitch.cfg` with two failed starts, a restart, an effort and two changes (1,359,356 states, 6 min 32 s on eight workers, capped at 900 s).

`SignIn` is the account's login arriving through the secret dialog (`docs/secrets.md`, `Supervisor::signedIn`): while starting is held back (`blocked`, after a `no-credential` or three failed starts) it lifts the hold and clears the failed-start count, as a prompt does, so what waits starts a driver without a restart or another prompt; with nothing held it does nothing. It counts as one of the person's changes (`MaxSwitches` bounds it), and the ghost `signin` marks the step so that `DownLeavesByWork` allows the cursor to leave down by it. The walk takes it on seeds that hold (2, 3 and 4 do). Per commit it has an instance of its own, `MCSupervisorSignIn.cfg`: two prompts, one failed start, no restart, nothing to change to, and one change, which is a sign-in or a change of the drivers file. The nightly wide instances take it among their other changes.

Properties: `UnknownRunsNothing` (invariant: while unknown, absent, no process, no turn open) and `NoSendUnknown` (no prompt is written in a step that starts or ends unknown, or to an AI out). `MCSupervisorAIUnknown.cfg` checks them per commit with one prompt, one restart and one removal (5,571 distinct states, 6 s on eight workers, capped at 75 s); `ais_functional_no_registry` and `ais_functional_no_registry_listed` check the same against the real server's drivers, the second with the AI's prompt queued and its session restarted with no registry.

The session's place: `dir` is its instance's directory (one of `Dirs`, or `""`), `here` whether the instance is on the server's machine; `SetPlace` changes them (`Supervisor::setPlace`, from the hub settling a session or an edit moving its instance) and counts as one of the person's changes. `ddir` is the directory the alive driver started in, `sdir` the one the harness session was made in (durable: the state's `sessionDir`), and `summary` that the next send owes a summary of the conversation (durable). Like an account change, a driver whose `ddir` is no longer `dir`, or any while not `here`, is ended once no turn is open. A start in another directory than `sdir` drops the harness session (`Drop`), and, when the conversation has turns, owes the summary, said in a notice; the next send carries it (`sum` in `written`). While not `here` no driver starts and nothing queued is taken; the activity shows down unless a turn runs on. Properties: `NoSendInOldPlace`, `PlaceKeepsTurn` (a move never ends a turn), `ResumesItsDir`, `SummaryOwed` and `SummaryCarried` (owed once, carried by the next send); `Settles` lets a prompt wait while the instance is elsewhere. `MCSupervisorPlace.cfg` checks them per commit with one directory, one change (a move, or the drivers file losing the driver) and a failed start (69,674 states, 33 s on four workers); nightly, `MCSupervisorPlaceWide.cfg` with two changes (a move and back) and a restart (219,868 states, 2 min 18 s on four workers, capped at 900 s). The main configs carry `Dirs = {}`, the place's moves still on (here and away).

The session's limit: `lim` is whether the session is limited to its directory (its AI's `limit`, or an account billed at API rate: `accounts::limitedFor`, `Supervisor::setLimited`), and the ghost `dlim` whether the alive driver was started limited (`--limit cwd`). `SetLimit` changes `lim` and counts as one of the person's changes. Tightened while a turn runs on a driver started without the limit, that turn is stopped in the same step, as the person's stop does (a stop written, then the stop's deadline), with a notice; a driver whose `dlim` is not `lim` is ended once no turn is open (`Retire`'s `OtherLimit`), and the next starts with `dlim = lim`. Loosened, the open turn finishes as it started. A driver may say hello without the `limit` feature (`"1n"`), and one started limited that does is ended. Properties: `NeverWeaker` (a driver started without the limit runs no turn for a limited session: it is starting, stopping or being ended), `NoSendWeaker` (no send is written to a driver weaker than the session's limit), `LooseningKeepsTurn`; `NoLatchedStop` allows the stop of a tightening. `MCSupervisorLimit.cfg` checks them per commit with one prompt and one change (4,497 distinct states, 4 s on two workers, in the supervisor-rest shard); nightly, `MCSupervisorLimitTwo.cfg` with two prompts, so a prompt behind the stopped turn is sent on the limited driver (54,428 distinct states, 29 s on eight workers), and `MCSupervisorLimitWide.cfg` with two prompts and two changes (tightened and loosened again: 156,441 distinct states, 68 s on eight workers, capped at 900 s). `MCSupervisorLimitAI.cfg` is `MCSupervisorLimit.cfg` with the AI also taken out of ais.json once and put back, so that a tightening and a removal meet (each stops an open turn; one stop is written), nightly (15,450 distinct states, 40 s on two workers). An AI out of the files reads limited (`accounts::Registry::limitedFor`), and one put back takes the limit its record says (`Drivers::present` sets it before `setPresent(true)`; ais_functional_ai_back_limited checks an AI taken out unlimited and put back limited). The other instances leave the change out (`LimitChanges <- NoLimitChanges`), so their state counts are as before. The directories a limited driver also keeps out (ais.json `"limit_keeps_out"`, `Supervisor::setKeepsOut`) are not a variable of their own: `lim` and `dlim` stand for the limit with them, so a directory added is a tightening (`SetLimit(TRUE)` on a weaker driver: the open turn stopped) and one removed a loosening (the driver ended once no turn is open). The walk does not change them; supervisor_test's limit group checks both against the code.

The window's state cursor (AGENTS.md "The state cursor") shows what the server works out per session: `ActivityOf(s)`, which `Supervisor::activity` computes and the trace binds at every step. `crashed` and `unconf` are the fields it adds to the state. `crashed` is set when a driver is abandoned (it crashed, broke the protocol or missed a deadline), cleared by a hello, and gone at a restart. `unconf` is the AI having no driver configured (the drivers file names none, or cannot be read): `Reconfigure` sets and clears it, as `Supervisor::configure` does when the server reads the file again (at each prompt, and each `kResolveMs` while an AI has none), and counts as one of the person's changes (`MaxSwitches`); while it holds, no queued prompt is taken and no prompt reaches the supervisor (the server refuses it first). "down" while starting is held back; else "busy" while a turn is open or about to begin (a prompt waits, a driver starts); else "down" while `unconf`, or while `crashed` unless the server is stopping; else "idle". The properties say what the colours promise: `IdleWaitsForPerson` (idle, steady dark blue, only with nothing running, waiting or to be taken: the AI waits for the person), `CrashShowsDown` (a driver that ends without being asked to never leaves the AI idle), `DownLeavesByWork` (red never quietly turns idle: only a prompt, a hello, a driver configured again, a restart or the server stopping move it), `NoDriverShowsDown` (an AI with no driver configured shows red, never idle, unless work still runs). `Settles` lets a prompt wait while the AI has no driver, until it has one again. The activity is in memory only (`Hub::setActivity`) and crosses the wire whole with each session, as its settings do: `Link.tla` does not model it, and `sync_unit` (`sessions_activity_and_tool_lines`, `hub_activity`, `mirror_activity`, `cursor_from_the_servers_state`) tests its carriage and the window's reading of it, grey whenever the link is lost. `ais_functional_stop`, `ais_functional_exit_mid_turn`, `ais_functional_queue_unconfigured` and `ais_functional_unconfigured` check it end to end over real driver processes.

The binding: `tests/server/supervisor_walk.cpp` (`supervisor_walk <seed> <steps> [--ais-churn [--faulty-remove | --faulty-unknown]] [--faulty-turn | --faulty-resume | --faulty-queue | --faulty-setting | --faulty-account | --faulty-activity | --faulty-dir | --faulty-limit] <out.tla>`) runs the real `Supervisor` against a scripted driver chosen from the seed (good turns, stops, wrong turns, bad lines, exits, silent starts, credentials, errors including `no-credential`, server restarts and a shutdown), the person's prompts sent and queued, changes of the session's model and effort and of its account, moves of its instance (between two directories, on this machine or another), the session's limit tightened and loosened, a hello with and without the `limit` feature, and the drivers file losing and regaining the driver, keeping the queue the store would hold (each take a dequeue) and checking it against the supervisor's, with the clock moved to each deadline and, one millisecond before it, checked to do nothing. It reads what the driver alive was told from the settings lines the code writes to it, applying each as a driver does, and records each send with that. It records each event with the code's whole state after it, and its activity (the state cursor's); `SupervisorTrace.tla` takes the `Supervisor` action each record names, `TraceMatches` requires the spec's state to equal the code's, and `ActivityOf` of it the code's activity, and every safety property is checked on the trace. Seeds 1 to 4 and 12 run per commit, 600 steps each (seeds 1, 3 and 12 stop a start; seed 12 then takes a queued prompt at the hello). With `--ais-churn` the walk also takes the AI out of ais.json and puts it back at random (`setPresent`, records `remove` and `back`), with no prompt sent while it is out, and one restart in three made holding no AIs list (`restart-unknown`), the next change of the AI then the first list read (`learn`, in or out); seeds 13, 14 and 15 run that per commit, 600 steps each (seed 15 learns the AI out and in, and restarts after an unknown restart). `--faulty-remove` records a removal that does nothing (a turn open runs on), on seed 13, and `--faulty-unknown` restarts with no list but the AI read as listed, on seed 13; TLC must report `TraceMatches` violated for each. The binding is shown to fail eight times besides: `--faulty-turn` loses the next turn number at a restart, `--faulty-resume` the session id, `--faulty-queue` the queue (on seed 12, whose walk restarts with prompts queued), `--faulty-setting` the model and effort (on seed 1, whose walk sets them before a restart), `--faulty-account` the account (on seed 2, whose walk sets an account before a restart), `--faulty-dir` the directory the harness session was made in (on seed 2, whose walk restarts with a session made in another directory than the first), `--faulty-limit` starts a restarted session unlimited (on seed 1, whose walk restarts while the session is limited), and `--faulty-activity` records a crashed driver's activity as idle; TLC must report `TraceMatches` violated. ## ClaudeDriver.tla: the Claude driver's turns

`ClaudeDriver.tla` models `drivers/claude/src/driver.ts`, the driver between the protocol (`docs/driver-protocol.md`) and one Agent SDK query. State: the credential check's `phase` (checking, ready, ended), whether the harness was started with a `--resume` id, the open turn and its `stage` (waiting behind the credential check or an unanswered interrupt, applying its settings, pushed into the query's input and still withdrawable, taken by the query), `stopping`, an open text block, an assistant's reported `failure`, `intFor` (the turn whose interrupt has not answered), the settings `pending` for the next send, the open turn's `carry` (not yet applied) and those `inUse`, the last turn, whether a `server` line before the first send named `"secrets"` (`secrets`), the open `ask-secret` number the running turn waits on (`asking`, 0 for none), and the last ask number minted (`asks`). History for the properties: the turns sent, the dones written per turn, what the last step wrote (`wrote`, kinds and turn or ask numbers), the latest settings received (`want`) and those at the open turn's send (`turnWant`), and whether the last step was a stop or secret answer and of which id (`act`).

The server is the environment (its `server` features before any send, sends after the last done, stops for any turn at any time, settings, `secret` answers including late ones from stopped turns, the end of input), and so is the query (the credential check's answer, including an API key, a failure, or a `--resume` id it does not know; reading a prompt; text, block ends, whole text blocks, tools; `nexus_ask_secret` calls; an assistant's error; the result, ok, error, or "no such session"; a refusal mid-turn (an API key in `init`, overage); the stream failing; an interrupt answered). While a turn runs without stopping after a `server` line naming `"secrets"`, with no other ask open, `nexus_ask_secret` mints the next ask number, writes `ask-secret` and holds the query's result until the matching `secret` line answers it or the turn stops; otherwise it answers the tool locally (`no-client`, `busy` or `cancelled`) without writing `ask-secret`. A stop ends what runs when it arrives: a prompt not yet read is withdrawn and the turn ends at once, one the query runs is interrupted and any open ask is cancelled at once so the turn does not wait on the server's dialog; a stop for a turn not open, or already stopping, changes nothing, and a late `secret` answer for a stopped ask is skipped. The next turn's start waits behind an unanswered interrupt. A turn takes the settings received before its send; a stop before it began gives them back under any newer ones. A lost `--resume` id closes the old query (cancelling its interrupt and any open ask), ends any open text block, starts a new session with the settings in use, and either ends a turn being stopped or starts the turn again there after the new credential check.

Invariants: `TypeOK`; `OneDone` (each turn sent has no done while open and exactly one once closed); `StopNeverLater` (while an interrupt has not answered, no other turn's prompt is in the query); `AskOnlyRunning` (an ask is open only while a turn runs without stopping on a server that offered `secrets`). Action properties: `NoDoneInBlock` (what a step writes keeps text blocks whole: no tool or done inside one); `AskGate` (`ask-secret` is written only during a running non-stopping turn with `secrets`, no other ask open, and the next ask number; `secrets` changes only before the first send); `SecretMatchesAsk` (only the open ask's own `secret` line settles it; any other is skipped); `SettingsNeverChangeOpen` (no settings change under a turn whose prompt is in the query); `SettingsFromNextSend` (a turn's prompt goes in with exactly the settings received before its send); `StopEndsWhatRuns`; `NoLatchedStop`. Liveness under fairness of the driver's own steps, the query's answers, and the server's bounded reply to an open ask (`Secrets.tla` `EveryRequestEnds`): `EveryTurnEnds` (every turn sent gets its done unless the driver exits, which the server cuts: `Supervisor.tla`), `InterruptsAnswered`.

Not modelled (unit-tested in `drivers/claude/test/unit`): a setting Claude refuses, and a model Claude cannot run going back to the one before (those tests are left out of the trace check); malformed `nexus_ask_secret` arguments refused locally before any state step; lines the driver refuses (sequence rule 4); costs, usage, session and credential lines; characters split across deltas.

Instances: `MCClaudeDriver.cfg`, three turns, one setting of two values, started with or without a `--resume` id (35,302 states, 6 s on four workers in CI), and `MCClaudeDriverSecrets.cfg`, two turns, two secret asks, one setting, with or without `--resume` (30,594 states, 5 s on four workers); nightly, `MCClaudeDriverTwo.cfg`, two turns and both settings (127,240 states, 12 s on eight workers), and `MCClaudeDriverSecretsWide.cfg`, three turns, two secret asks and two setting values (197,452 states, 20 s on eight workers).

## Glide.tla: the sprint board's scrolling

`Glide.tla` models `nexus::GlideScroller` (`src/scroll_glide.h`), which animates the board's scroll for the keys and the mouse wheel. The page's scroll is `pos` in `0..Max`; the band drawn past an end is `over`. The motion is `mode`: `idle`, a `coast` easing to `target` (exponential decay), a `hold` running while an arrow is down, or a `spring` taking the band back to an end (critically damped). Time is frames of `Dts` ticks; a coast or a spring that has not settled by its cap (`CoastTicks`, `SpringTicks`) lands where it was going. The curves are abstracted: each frame moves the page any amount the right way, up to the target, so a curve that overshoots or turns back is caught by the properties. The actions are an arrow pressed (`Press`), its OS repeat (ignored), its release (`Release`; the window losing focus is a release too, as Prax sends a key-up for every held key on resign), another key (`Key(d)`: a page, an end), a notch (`Wheel(d)`), a trackpad's scroll or a press of the pointer (`Interrupt`), the page's own script scrolling (`Page(y)`), the board leaving the screen (`Hide`), and `Frame(dt)`.

| Property | Kind | Says |
|---|---|---|
| `InRange` | invariant | the scroll is in its range, the band under the view's height |
| `BandAtEnds` | invariant | the band only at an end, on its outer side |
| `ShowsItself` | invariant | while a motion runs, the page shows what the scroller last set |
| `SpringAtEnd` | invariant | a spring stays at its end and never swings into the page |
| `HeldOnlyPressed`, `HoldIsHeld` | invariant | only an arrow held down holds |
| `EventsKeepPlace` | action | an event never moves the page itself: what it starts moves from where the page shows |
| `NeverBack` | action | a coast or a hold, and every event during one, never moves the page back against its way (a retarget never jumps back) |
| `PadStops` | action | a trackpad's scroll or a click stops the motion and the hold |
| `Settles` | liveness | once input stops, the page comes to rest and nothing is held |

`MCGlide` is the instance: a page of 3, lines of 1 and keys of 2 or 3, 15,668 states in about 2 s.

| Witness | Broken | Rejected by |
|---|---|---|
| `WGlideJumpBack` | a key restarts the motion from where it began | `NeverBack` |
| `WGlideClampTop` | no clamp at the top | `InRange` |
| `WGlidePadKeeps` | a trackpad's scroll leaves the motion running | `PadStops` |
| `WGlideLostKeyUp` | a release is lost, so the hold runs on | `Settles` |
| `WGlideSpringInside` | the spring overshoots into the page | `SpringAtEnd` |
| `WGlideSpringForever` | the spring never settles | `Settles` |

The binding: `tests/model/glide_walk.cpp` (`glide_walk <seed> <steps> [--faulty-keyup] <out.tla>`) drives the real `GlideScroller` over a fake page in whole px (2000 of scroll, 800 high, lines of 40) with a seeded walk of presses, repeats, releases, page and end keys, notches, trackpad scrolls, clicks, the page's own scrolls, hides and frames of 4 to 33 ms, in time it counts itself. `GlideTrace.tla` pins each step's next state to the record (scroll, band, motion, target, cap left, hold) and takes the `Glide` action it names; a step the spec cannot take is a deadlock. Five seeds of 1000 steps run per commit; `--faulty-keyup` walks a scroller that loses the arrow's release, and TLC must report the deadlock.

## Overlay.tla: when the overlay shows and hides

`Overlay.tla` is when the overlay shows and hides: `nexus::OverlayRules` in `src/overlay.h`, with the window that carries out its answers (`main.cpp` `carryOut`, through Prax) and the OS around it. Variables: `visible` (`prAppWindowIsVisible`), `active` (`prAppWindowIsActive`: the overlay has the keyboard), `keyed` (the rules' note that it has had the keyboard since it was last shown), `armed` (the key check after a show is pending, a Prax timer), `last`, the input just handled and the act answered, and `held`, whether nexus holds the window (`main.cpp` `a.window`): `carryOut` acts only on a window it holds. Inputs: `Hotkey`, `Escape`, `Observe` (a frame; a change of `visible` or `active` asks for one) and `KeyCheck`. The OS: a show gets the keyboard or not, `Lose` (Command-Tab, a click on another app), `Click` (a click on the overlay gives it back). Prax: `Open`, the window's open, which comes only with a frame of a shown window (a hidden window has no frames). `start()` creates the overlay window itself, so `Init` holds it from the start. `Spec` has weak fairness on `Observe` and `KeyCheck`: the frames and the check that a change asks for do come.

| Property | Kind | What it says |
|---|---|---|
| `TypeOK` | invariant | every variable has its type, and every act is one the window knows |
| `KeyedOnlyVisible` | invariant | only a shown overlay has had the keyboard |
| `UnkeyedIsChecked` | invariant | a shown overlay that has not had the keyboard always has a key check coming |
| `HotkeyShows` | action | the hotkey shows the overlay from every state but up with the keyboard (after Command-Tab the next press shows it, not merely re-activates it) |
| `HotkeyHides` | action | the hotkey hides an overlay that is up with the keyboard |
| `EscapeHides` | action | Escape hides it |
| `NoHideWhileActive` | action | a frame or the key check never hides an overlay that has the keyboard (an input method's window or the emoji picker, which leave it the keyboard, cannot hide it) |
| `NoHideBeforeKey` | action | a frame never hides an overlay that has not had the keyboard since it was shown |
| `LossHides` | action | once it has had the keyboard, the frame that sees it lost hides it |
| `RefusedShowHides` | action | the key check hides an overlay shown without the keyboard |
| `NeverStranded` | temporal | a shown overlay without the keyboard is in time hidden or has it again |

`Overlay.cfg` checks every property on the whole state space (19 states). Each property has a witness in `witnesses/` (`WOverlay*`): `WOverlayActName` (Escape answers an unknown act: `TypeOK`), `WOverlayEscapeKeepsKeyed` (`KeyedOnlyVisible`), `WOverlayShowUnchecked` (a show arms no check: `UnkeyedIsChecked`), `WOverlayHotkeyHidesUnkeyed` (`HotkeyShows`), `WOverlayHotkeyOnlyShows` (`HotkeyHides`), `WOverlayEscapeIgnored` (`EscapeHides`), `WOverlayHideWhileActive` (`NoHideWhileActive`), `WOverlayHideBeforeKey` (`NoHideBeforeKey`), `WOverlayLossKept` (`LossHides`), `WOverlayRefusedKept` (`RefusedShowHides`), `WOverlayStranded` (neither a frame nor the check hides: `NeverStranded`, expected as a temporal violation) and `WOverlayHeldAfterOpen` (nexus holds the window only from its open, as the first lib/app overlay did, so a window that starts hidden is never held and the hotkey shows nothing: `HotkeyShows`).

The binding: `tests/model/overlay_walk.cpp` (`overlay_walk <seed> <steps> [--faulty-hide-unkeyed | --faulty-hotkey-hides] <out.tla>`) drives the real rules with a seeded random walk over a stand-in window that carries out their answers as `carryOut` does, and writes `OverlayTraceData.tla`. `OverlayTrace.tla` takes the `Overlay` action each record names, with the OS's answer to a show from the record, and `TraceMatches` requires the spec's state and act to equal the code's; every `Overlay` safety property is checked on the trace. Three seeds of 1000 steps run per commit; `--faulty-hide-unkeyed` (a frame hides any shown overlay without the keyboard) and `--faulty-hotkey-hides` (the hotkey hides any shown overlay) must each be rejected with `TraceMatches` violated. `held` is not in the walk: its stand-in window exists from the start, as `start()`'s does, and the trace check requires `held` throughout; that `start()` creates the window is read from the code, not traced.

## ClientLock.tla: the client lock

`ClientLock.tla` is the lock every window keeps (`docs/security.md`): `nexus::ClientLock` in `src/client_lock.h`, with the system's authenticator and the OS around it. Variables: `state` (`locked`, `prompting` while the system's prompt is up for the current attempt, `unlocked`), `why` (what the lock screen says: `launch`, a relock event, `idle`, a refusal; `none` while unlocked), `attempt` (the number of the last prompt), `pending` (attempts whose answer has not come back: the authenticator answers every attempt it was given, late ones included), `idle` (seconds without input while unlocked), `granted` (the attempt whose grant unlocked it) and `last`, the step just taken with its argument, its attempt, the seconds it let pass, and what the code answered (a frame: whether it drew content; input: whether it was delivered). Actions: `Prompt` (from `locked` only; `PromptIgnored` otherwise), `Answer(n, a)` (`granted`, `failed`, `cancelled`, `unavailable`; only the current attempt's, while it is asked, counts), `Relock(r)` (`sleep`, `screen`, `switch`, `background`, from any state), `Tick(d)`, `Input` and `Frame`. `Spec` has weak fairness on the answers: the system answers what it is asked.

| Property | Kind | What it says |
|---|---|---|

## Accounts.tla: accounts, AIs, and the account each session runs on

`Accounts.tla` models what `src/sync/hub.h` decides about accounts (`src/accounts/registry.h`; the files are `docs/accounts.md`): the accounts, each `"absent"`, `"in"` (signed in) or `"out"` (needs sign-in), with its provider; the AIs set up; each AI's linked accounts, in order, and its default or none; each AI's instances (the AI on one machine in one directory), in order, the first its default instance; and each session's AI, instance (or none), account (or none) and harness. ## Secrets.tla: the secret dialog

`Secrets.tla` models the secret dialog (`docs/secrets.md`): an asker (an AI through its driver, or the server's own sign-in) asks `nexus-server` for a secret for an account; the server mints a request id (durable, never reused across restarts) and puts the request, never a value, in the state every connected window receives; each window that can take requests shows a dialog for the oldest open one it has not answered; a person pastes the value once into one window, which sends it up its actions to the server alone, or presses Escape, which cancels it for every window; the server takes the first answer for an open request, writes the account's file and answers the asker `stored`, or answers `refused` with a reason (`busy`: one is already open, or a value held, for the account; `no-client`: no connected window can take one, none at all or only windows from before secret requests; `cancelled`; `timeout`; `malformed`: a value in `BadValues`, not of a token's shape). One chance (docs/secrets.md): the account's disk may fail (`DiskFails`, at most `MaxFailures` times) and heal (`DiskHeals`); a write while it fails may or may not land, and either way the value is held (`held`, state `holding`), not refused, and written again (`Retry`, `RetryFails`) until the write is durable, and only then is the asker answered `stored`. A request past its deadline ends `expired`, and an answer that crossed the deadline is still stored while its request is the newest of its account; at a restart, an expired request becomes `refused`, and a held value is lost (`lost`: the one documented window). `taken` is the value the server received for each request. An answer for a request no longer open is dropped and logged without its value. A restart drops every open request unanswered (its asker went with the server). A window that loses its link or quits loses its dialog and what was typed in it. A value is an opaque token (`Values`); `replies`, `transcript` (what the asker's session shows: its AI reads it back) and `log` (server.log) hold, for the last two, the lines the last step wrote, so an invariant on them covers every line ever written without the state growing with the history.

Invariants: `TypeOK`; `NoSecretToAsker`, `NoSecretInTranscript`, `NoSecretInLog`, `NoSecretToWindows` (no value in a reply, a session line, a log line, or any window's received state); `AtMostOneStored` and `StoredWhenStored` (one write per request, exactly when it ended stored); `OneOpenPerAccount`; `AnsweredOnce` and `AnsweredWhenEnded` (an asker hears exactly one answer for a request that ended stored or refused, none for one dropped at a restart); `ReceivedNeverDropped` (the owner's one-chance rule: a value the server received is stored, or held and being written again, or, after a restart, in `lost`; never dropped while the server runs); `StoredOnlyDurable` (`stored` only once the file holds the value); `HeldOnlyWhileHolding`; `NoMalformedStored`. Action properties: `ClosedStaysClosed` (an ended request never changes again: never satisfied late, never reopened, its id never reused; an expired one only to `stored` by its crossing answer, or to `refused` at a restart); `AskNeedsTaker`; `HeldOnlyStored` (a held value leaves only by being stored, or lost at a restart). Liveness, under fairness of deadlines, windows receiving the state, answers arriving, the disk healing and retries (never of a person answering): `EveryRequestEnds`, `DialogsClose` (every window's dialog for an ended request closes), `HeldIsStored` (a held value is stored in the end).

Instances, per commit: `MCSecrets.cfg` (two windows, one request, one restart: 2,355 states), `MCSecretsOne.cfg` (one window, two requests for one account: 3,763), `MCSecretsOld.cfg` (a window and an older one: 348). Nightly: `MCSecretsTwo.cfg` (one window, two accounts: 26,270), `MCSecretsWide.cfg` (two windows, two requests, one restart: 185,973) and `MCSecretsMixed.cfg` (a window and an older one, two accounts, two askers: 226,340). Witnesses (`WSec*`): `WSecReplyCarriesValue` (`NoSecretToAsker`), `WSecTranscriptValue` (`NoSecretInTranscript`), `WSecLogValue` (a late answer logged with its value: `NoSecretInLog`), `WSecRelayToWindows` (`NoSecretToWindows`), `WSecStoreTwice` (the latest paste wins: `AtMostOneStored`), `WSecLateStored` (an answer after a cancel or the deadline stored: `ClosedStaysClosed`), `WSecIdsReused` (ids counted in memory, from 1 after a restart: `ClosedStaysClosed`), `WSecTwoOpen` (`OneOpenPerAccount`), `WSecReplyTwice` (a late answer answered to the asker: `AnsweredOnce`), `WSecNoClientOpens` (`AskNeedsTaker`), `WSecNoTimeout` (`EveryRequestEnds`) and `WSecDialogStays` (a window keeps its dialog after another answered: `DialogsClose`), the last two as temporal violations. The one-chance rule's: `MCSecretsBad.cfg` (per commit: one window, one request, a value not of a token's shape, the disk failing once: 2,771 states) passes, and these are rejected, each also on `MCSecretsBad.cfg`'s own constants; `MCSecretsBadTwo.cfg` (the same with two requests, so a malformed paste is asked again and a crossing answer can be made stale by a newer request: 168,610 states, 57 s) passes nightly: `WSecDropOnFailure` (a value whose file cannot be written refused `unwritable` and dropped, as before the rule: `ReceivedNeverDropped`), `WSecLateAfterDeadline` (an answer that crossed the deadline dropped: `ReceivedNeverDropped`), `WSecStoredBeforeDurable` (`stored` answered for a write that did not land: `StoredOnlyDurable`), `WSecMalformedStored` (a paste not of a token's shape written: `NoMalformedStored`) and `WSecHeldNeverRetried` (a held value never written again: `HeldIsStored`, a temporal violation). `WSecBusyIgnoresHeld` (an ask beside a held value not refused busy, only an open request counted: `OneOpenPerAccount`) is rejected per commit on its own instance, two requests and the disk failing once (541 states). With the disk's variables, `MCSecrets.cfg` and `MCSecretsWide.cfg` fail it once; the state counts above are from before them.

The binding: `tests/sync/secrets_walk.cpp` (`secrets_walk <seed> <steps> [--format 3|4] [--faulty-store-late | --faulty-echo | --faulty-driver | --faulty-driver-echo] <out.tla>`) drives the real code as the server and the windows wire it: `Drivers` over an in-memory `Drivers::Host` harness (`ask-secret` written on each driver's standard output, `Drivers::hold` and `Drivers::release` around each step, and every session asker's reply decoded off its driver's standard input), `Hub::askSecret`, `apply`, `expireSecrets`, `retrySecrets` and `dropSecrets` over a `MemoryStore` (a restart ends `Drivers` and starts a new `Drivers` and `Hub` over the same store, so ids come from the store's counter), each window's state as the hub's `Sessions` sent as a diff in its format (3 or 4, or 2 for an older window, which must never receive a request) and given to its `SecretPrompt`, and each answer or cancel an action encoded by `Actions` in that format and parsed back before the hub applies it, received in any order. ## Tailscale.tla: a Tailscale node's lifecycle as the host sees it

`Tailscale.tla` models a node of the Tailscale shim (`docs/tailscale.md`, "Layer 1"): the facts tsnet and control give (the backend's state, a sign-in URL, a finished login, an error message or logged error, a network map received, the map poll closed, the self node's key expiry), the host's start (with an auth key or without, against a control server whose certificate is trusted or not), close and new login, the table of state directories held, and the world those facts come from: control up or down (`CtlDown`, `CtlUp`), directories control has enrolled, keys control has expired, the person's approval. tsnet's actions are guarded by that world (`TsNeedsLogin`, `TsKeyAccepted`, `TsKeyAcceptedQuiet`, `TsStarting`, `TsRunning`, `TsNetMap`, `TsPollClosed`, `TsRefuse`, `TsRateLimited`, `TsCertFail`, ...), so a fact the world could not produce is not a behaviour. The state the host sees is derived from the facts (`lifecycle.derive` in `src/tailscale/lifecycle`, which the shim calls for every state it reports), with `ControlDown` beside it. Invariants: `TypeOK`, `ReadyHasPeers` (ready only when running with a map since the start or sign-in), `ClosedNeverRunning`, `URLOnlyInNeedsLogin`, `OneNodePerDir`, `StatesNamed`, `CertNeverReady`. Liveness: `GetsReady` (a started node never closed, its certificate trusted, ends ready, and again after each expiry, outage or refusal) and `CertFails` (an untrusted certificate ends failed with reason `certificate`, a state the node may stay in for good).

The fairness, stated honestly: the liveness holds only if the person approves a sign-in URL that stays shown, the host calls `nts_login` whenever the node stays expired, failed or waiting with no URL, control comes back up once down, and tsnet keeps taking its steps. These are assumptions about the outside world, not things the shim does or could make true; without them nothing reaches ready, and the model claims nothing then.

Instances, per commit, each with two node slots on one directory, one outage, one expiry and one refusal: `MCTailscale.cfg` (interactive starts, trusted certificates: 47,169 distinct states, 10 s), `MCTailscaleKeys.cfg` (starts with and without a key, no expiry: 68,635, 16 s), `MCTailscaleCerts.cfg` (certificates trusted or not: 74,329, 17 s); times measured on the studio under load. Witnesses (`witnesses/WTs*`, each a `Broken` fault): `WTsReadyWithoutPeers` (`ReadyHasPeers`), `WTsURLKept` (`URLOnlyInNeedsLogin`), `WTsClosedRuns` (`ClosedNeverRunning`), `WTsTableIgnores` (`OneNodePerDir`), `WTsCertIgnored` (`CertNeverReady`), `WTsNoRelogin` and `WTsPollIgnored` (`GetsReady`, temporal violations).

Recorded orders: `TailscaleOrders.tla` with `TailscaleOrders_{restart,authkey,cert,starting}.cfg` takes an order of node 1's facts seen from the real shim against the test control server (a restart running straight from its own state, then ready; an auth-key start with no sign-in; a certificate failure first; an interactive restart by way of starting) and requires `Next`, the world's actions included, to produce it: `OrderNotReached` must be violated.

The binding: `src/tailscale/lifecycle/walk` (`go run ./walk <seed> <steps> <out.tla> [--faulty-ready | --faulty-url | --faulty-close | --faulty-table | --faulty-down]`, run by tlc.cmake's `TSWALK`) plays the model's world (16 node starts on 3 directories, at most 12 outages, 8 expiries and 12 refusals, written into the trace as `TraceMaxOutages`, `TraceMaxExpiries`, `TraceMaxRefusals`) and drives the real `lifecycle` code with only the events that world can produce, recording each with the code's state after it; `TailscaleTrace.tla` maps each record to the spec's action of that name, so the record must be a step of the spec's world as well as of its node, and the spec's state must equal the code's at every record. ## SignIn.tla: a claude account's sign-in in the browser

`SignIn.tla` models in-app sign-in (`docs/secrets.md` "Sign-in"). The server marks an account `Need`ed (`next`, the next flow id, durable across `Restart`); a flow's `st` is one of unused, needed, started, url-sent, waiting, callback-forwarded and its ends, captured, failed, cancelled, expired and dropped. Windows (`Clients`, some `Remote`: on another machine than the server) `Connect` and `Disconnect`, are `Show`n by the person (`armed`), `Sync` the state into their own `view` (`PubFor(c)`: a flow's opener is none, the window itself, or `Held` by some other window, and its URL only for the holder), `Claim` the oldest offer no window holds that they have not `claimed`, and `Open` a flow they hold with its URL (`opened`; a remote window binds its `gate` first). The server's side receives the actions `up` (claim, opened, callback, each from a window, in any order and possibly twice), runs at most one process per account (`proc`, `procs`), takes its `Url`, replays a matching callback (`cbs`; a non-matching one would land in `badcb`), takes the `Print`ed token into the one-chance store (`file`, `held`, `disk`, `failures`, `Retry`, `DiskFails`, `DiskHeals`), or ends it (`Exit`, `Timeout`). A flow's deadline and its process's end are two steps: `Timeout` (and every other end) only tells the process to end (`proc.ending`), and `End` is the process ending a moment later; a token it `Print`s in between, late, is stored all the same and a needed flow for the account ends dropped (`said`, ghost: what each flow's process printed). `FallBack` ends a flow no window holds (needed, or running after its window went) dropped when only windows from before sign-ins are linked, its process told to end, and opens the paste asked for instead (`ask`, unless the account is signed in or its login held); `AskEnds` is that paste ending without a value, and a login stored for the account (`Print`, `Retry`) closes it; a new flow waits while it is open. The browser's `Redirect` goes to Claude Code's listener on the server's machine or to the window's gate, and a `Stray` request may hit the gate. A remote window's `Open` of a flow that needs a gate waits while its gate is bound for another (`OpenWith`). `Lose` is a login that ended (`losses`); `signedin` per account; `taken` the token captured per flow; `log` the last step's log lines.

Invariants: `TypeOK`; `OneFlowPerAccount` (no second flow from a second window, a reconnect or a second report); `OneProcessPerAccount`; `ProcessHasItsFlow` (a process runs, not ending, exactly while its flow runs); `EveryPrintTaken` (every token a process printed, in time or late, is taken); `GateForEveryPage` (every page a remote window opened for a flow it holds and that waits has that window's gate); `OneCallbackPerFlow` (exactly one callback forwarded); `CallbackOnlyMatching` (only with the URL's state, from the holder); `GateForwardsOnlyMatching` (a gate sends up only the matching callback: Claude Code's listener ends the whole login on a wrong request); `TokenNeverDropped` (a captured token is stored, held and written again, or lost only at a restart); `HeldOnlyCaptured`; `SignedInHasLogin`; `NoAskWhenSignedIn` (no paste is asked for an account signed in); `NoTokenInLog`; `NoTokenToWindows` (no window's view holds a token). Action properties: `ProcessOnlyFromNeeded` (a process starts only from a needed flow's first claim); `EndedStaysEnded`. Liveness, under fairness of deadlines, processes ending, the disk healing and retries: `RunningEnds`, `HeldIsWritten`, `ProcessEnds`.

Instances, per commit: `MCSignInOne.cfg` (one remote window, one account, one token, one flow, one disk failure), `MCSignInTwo.cfg` (a window on the server's machine and a remote one, the safety properties) and `MCSignInGate.cfg` (one remote window, two accounts, two flows: a second page waiting on the window's one gate). Nightly: `MCSignInTwoLive.cfg` (the same instance as `MCSignInTwo` with `RunningEnds`, `HeldIsWritten` and `ProcessEnds`, whose check over this graph is past a per-commit run's time on a CI host). The state counts are in `tests/model/CMakeLists.txt`. `MCSignIn.cfg` (two flows, a restart, a lost login) is a bench run, not a test. Witnesses (`WSignIn*`, each rejected by the rule it breaks): `WSignInClaimStarts` (every claim of an unheld flow starts a process, a running one too: `OneProcessPerAccount`), `WSignInStrayForwards` (a gate that sends up any request: `GateForwardsOnlyMatching`), `WSignInReplayAny` (that gate and a server that replays any callback: `CallbackOnlyMatching`), `WSignInDropToken` (a captured token whose write fails is dropped: `TokenNeverDropped`), `WSignInTokenInLog` (the capture's log line holds the token: `NoTokenInLog`), `WSignInNeedTwice` (a second report mints a second flow: `OneFlowPerAccount`), `WSignInExpiredKeeps` (an expired flow's process left running: `ProcessHasItsFlow`), `WSignInLateDropped` (a token printed after its flow ended is dropped: `EveryPrintTaken`), `WSignInAskKept` (a login stored late leaves the paste asked for open: `NoAskWhenSignedIn`), `WSignInGateTaken` (a second page opens while the window's gate is bound for the first: `GateForEveryPage`) and `WSignInNoTimeout` (no deadline: `RunningEnds`, a temporal violation). `WSignInStrayHostile.cfg` must pass: with the hostile gate, the server's own check still replays only the matching callback, once.

The binding: `tests/sync/signin_walk.cpp` (`signin_walk <seed> <steps> [--faulty-claim | --faulty-callback | --faulty-stray] <out.tla>`) drives the real `Hub` (its `SignInDesk` over a `MemoryStore`, and the one-chance store's real desk over a keeper, a map of login files, that fails while the walk's disk fails), two accounts, and two windows (one remote), each a real `SignInOpener` fed the hub's `stateFor` its claim token as a diff in the state format, its actions encoded and parsed back, and a real `CallbackGate` for the remote one. The walk plays the processes (the runner's hooks record each start, stop and replay), the browsers, the person, the links (actions delivered out of order and twice), the disk, the clock and restarts (a new `Hub` over the same store). After each step it writes the code's state as the model's variables, all but `log`, and fails at once on any log line that holds a URL, a code or a token. `SignInTrace.tla` checks first the code's own record against the rules (`CodeOneProcessPerAccount`, `CodeOneCallbackPerFlow`, `CodeCallbackOnlyMatching`, `CodeGateForwardsOnlyMatching`, `CodeNoTokenToWindows`, `CodeOneFlowPerAccount`), so that TLC names a broken rule, then each variable group (`MatchServer`, `MatchCallbacks`, `MatchWindows`, `MatchViews`, `MatchGates`, `MatchUp`, `MatchStore`), then `TraceMatches` and every `SignIn` safety property on the trace. Seeds 1 to 4 run per commit, 6000 steps each (`tlc_signin_trace_seed_*`); between them they claim, take over, open, redirect, stray, time out, print in time and late, end a process told to end, fall back to a paste (`Hub::signInWindowsChanged` with only older windows, then the paste cancelled and the account asked for again by `requestSignIn`), retry a held token, lose a login and restart. The binding fails three times on purpose: `--faulty-claim` (`SignInDesk::injectClaimFault`: a takeover starts a second process) by `CodeOneProcessPerAccount`, `--faulty-callback` (a callback replayed whatever its state, twice) by `CodeOneCallbackPerFlow`, `--faulty-stray` (`CallbackGate::injectStrayFault`: the gate takes any GET) by `CodeGateForwardsOnlyMatching`. ## Reconnect.tla: the window making its session again when its server is gone

`src/link/client.h`, with the decision in `src/sync/redial.h` (`Redial`). `Link.tla` is what a session carries once made; this is how the window gets one. Servers start and go (`Start`, `Gone`: a handover's exit, a stop or a crash), each started a new one on the same store; a server that stops may tell the window it ended the session (mosh's shutdown; the message may be lost, and a crash tells nothing). The window runs the bootstrap (`Dial`) when it holds no session or the one it holds is lost (ended by its server, or quiet: not heard for `kQuietMs`), once the backoff after its latest attempt has passed; a bootstrap reaches the server running, or fails and keeps what was held. `Hear` is the session's server's state arriving, which ends the backoff; `Time` ends a backoff or makes a session quiet. Fairness is on `Dial`, `Hear` and `Time`, never on servers coming and going.

Properties: `DialsLive` (every session made is with the server running then, never one from an old `CONNECT` line), `NeverBack` (once it holds a server's session, the window never holds an earlier one's), `Reconnects` (while a server is up, the window comes to hold its session and hear it, or the server goes first), with `TypeOK`.

Instance, per commit: `MCReconnect.cfg` (three servers in turn: 320 distinct states). Witnesses (`WReconnect*`): `WReconnectCached` (a session made again from the kept `CONNECT` line with no server: `DialsLive`), and, as temporal violations of `Reconnects`, `WReconnectOnce` (the bootstrap only while no session was ever made: the window before this module), `WReconnectOnlyEnded` (a session made again only when its server said it ended, never after a crash) and `WReconnectGivesUp` (a backoff that never ends).

The binding: `tests/sync/reconnect_walk.cpp` (`reconnect_walk <seed> <steps> [--faulty-cached | --faulty-no-reset] <out.tla>`) drives the real `Redial` as the link thread does, with a seeded walk and a made-up clock (from 1000 s), playing servers started and gone (up to eight), the shutdown reaching the window or not, bootstraps run exactly when `Redial::due` says, the server heard, and the clock moving past backoffs and `kQuietMs`; `ReconnectTrace.tla` checks that each record is a step of the spec. Seeds 1 to 4 run per commit, 1000 steps each (CI shard `reconnect`). The binding is shown to fail twice: `--faulty-cached` makes a session again from the old line with no server running, `--faulty-no-reset` starts a new backoff when a server is heard; TLC must reject both. What the model leaves out (the backoff's lengths, the actions resent from `--next`, the real bootstrap and mosh) is `sync_unit_redial`, `link_unit` `bootstrap_command_reconnect` and `link_e2e_takeover`, which stops a server cleanly and kills one, under a throwaway HOME, and checks the window keeps a stopped server stopped, shows the new server's state once started, and applies every action once.
## RelayLife.tla: the native window on Windows and the relays that carry its link

`src/relay/relay_life.h` (`RelayLife`), driven by `src/relay/relay_port_win.cpp` (`RelayPort`). On Windows the window's link runs inside WSL2 as `nexus-link-relay` (mosh's transport does not run natively there); the window starts it with `wsl.exe`, writes it its Hello and its actions, and reads its Hello and the link's state. A relay can end at any time (it crashed, WSL2 stopped, its bytes were not the protocol); the window then starts another after a backoff, and the new relay is a new link with a new client id, as a new launch of the window is. The window numbers its actions across every relay (`Send`); each is written to the live relay once, in order (`Write`), and one not written when a relay ends waits for the next. The server applies what each relay's link delivered, per link in order, once per link (`Apply`, with no guard on the relay being live: what was in flight may still arrive). The live relay's state tells the window how far the server applied its actions (`Ack`), only after its Hello (`Hello`). When a relay ends (`Death`, only once its process has exited) the actions written to it and not acknowledged are cut: never written again, and handed to the window's poll (`Tell`) to show. The backoff is 1 s, doubling to at most 10 s, and 1 s again after a relay that ran 10 s or more (`Tick` is one second). The window's exit (`Stop`) writes nothing more and starts no relay; its relay then ends by itself (`Exit`).

Properties: `OneRelay` (never two relay processes at once), `AppliedOnce` (the server applies each action at most once), `AckTrue` (every action the window counts acknowledged, the server applied), `Covered` (while the window runs, every action written is acknowledged, cut, or with the live relay: none lost silently), `BackoffOK` (the backoff is 1, 2, 4, 8 or 10 s), with `TypeOK`; `CutOnlyUnacked` (a relay's end cuts only actions not acknowledged) and `WaitsBackoff` (a relay starts only when the backoff is over and no relay process runs) as action properties; `CutTold` (every action cut reaches the window's poll, unless it exits) and `Restarts` (with no relay, one starts) as temporal ones.

Instances, per night (CI shard `relay`): `MCRelayLife.cfg` (three relays, three actions: 24,417 distinct states, 11 s on four workers) and `MCRelayLifeBackoff.cfg` (six relays, one action, the backoff to its cap: 5,156). Witnesses (`WRelay*`): `WRelayResend` (the unacknowledged actions written again to the next relay, which the server cannot tell from new ones: `AppliedOnce`), `WRelaySilent` (a relay's end that cuts nothing: `Covered`), `WRelayTwo` (the next relay started before the last one's process exited: `OneRelay`), `WRelayNoBackoff` (`WaitsBackoff`), `WRelayUncapped` (a backoff that doubles with no cap: `BackoffOK`), `WRelayAckEarly` (an acknowledgement of what was only delivered: `AckTrue`), and, as temporal violations, `WRelayUntold` (`CutTold`) and `WRelayStuck` (a backoff that never runs out: `Restarts`).

The binding: `tests/relay/relay_walk.cpp` (`relay_walk <seed> <steps> [--faulty-resend | --faulty-early-end | --faulty-ack-delivered] <out.tla>`) drives the real `RelayLife` as the port does, with a seeded walk and a made-up clock: the window's actions (each with its number as its text, so that the walk's world knows an action by its bytes, not by the code's numbers) and polls; relays started when `mayStart` says so and only once the last one's process exited; the bytes `take` hands over read by a real `RelayServer` per relay; each relay's Hello, and its link's state as real `StateWriter` frames carrying the server's first unapplied action; the server applying what each relay's link delivered, a relay that ended included; relays that crash or send bytes that are not the protocol; the clock by whole seconds while `RelayLife` waits; and, near the end, the window's exit. `RelayLifeTrace.tla` checks that each record is a step of the spec. Seeds 1 to 4, 1000 steps each, per night, with TLC and under the sanitizers. The binding is shown to fail three times: `--faulty-resend` hands the cut actions over again (the next relay is written an old action under a new number), `--faulty-early-end` reports a relay ended when its output closes, before its process exits, `--faulty-ack-delivered` has the relays report as applied what they delivered; TLC rejects all three. What the model leaves out (the frames and bytes, mosh and the link inside a relay) is `relay_unit`, `link_unit`, and the functional `wsl2_link` on captain, which kills the relay across the real boundary and checks the window shows it, starts the next and goes on numbering, with nothing applied twice.
## LoopPass.tla: one pass of nexus-server's loop

`LoopPass.tla` models one pass of `nexus-server`'s serving loop (`src/server/pass.h` `PassOrder` and `take_pass_step`, `src/server/server.cpp` `Server::run`, `src/server/drivers.cpp` `Drivers::hold` and `release`, `src/server/durable.cpp` `DurableStore::beginBatch` and `flush`), repeated across passes, batches of client actions and driver messages, store failures and crashes at any point.

Each pass runs in `DefaultOrder`: `"tick"` (every link ticks at the top of the pass: the state staged at the end of the previous pass leaves on the wire as `sentSnap`, and mosh acknowledges only client actions received before that flush, `acked`), `"hold"` (`DurableStore::beginBatch` and `Drivers::hold`: commits append to `batch` in memory without syncing, and commands told to a driver wait in `heldCmds`), `"apply"` (driver `Hello` / `Done` through `Drivers::serve`, and client `Send` / `Queue` / `Stop` ranges received and applied in order through `Applier`, `Hub::apply` and `Drivers`), `"flush"` (`DurableStore::flush`: one sync makes every record of `batch` durable on `disk`), `"release"` (`Drivers::release`: held commands go out to the live driver in order), and `"state"` (when the pass changed anything, `ServerSession::setState` stages `linkSnap` for the next pass's tick). A failed apply or flush stops the loop (`failed = TRUE`) before release, state or another tick. `Crash(k)` may happen at any point, keeping any prefix `0..Len(batch)` of the current batch's records on disk (covering volatile loss and torn batch writes between `log_->append` and `log_->sync` on `MemFs`), cutting any open turn with a notice without resending its prompt, taking the oldest queued prompt when nothing waits, and reconnecting each window from `acked[c] + 1` with `Applier(disk.applied[c])`.

| Property | Kind | What it says |
|---|---|---|
| `TypeOK` | invariant | every variable, counter and phase stays in range |
| `ExactlyOnce` | invariant | every window's actions are applied in order `1..applied[c]`, each at most once, across crashes, torn batch prefixes and reconnections |
| `PromptAtMostOnce` | invariant | each prompt is written to a driver at most once across all passes, partial flushes and crashes |
| `TurnsIncrease` | invariant | turn numbers written to drivers start at 1 and strictly increase across crashes |
| `DriverOnlyDurable` | invariant | nothing reaches a driver (neither a prompt's send nor a stop) before the batch that decided it is durable on disk |
| `LinkStateDurable` | invariant | neither the state staged on links (`linkSnap`) nor any state sent to windows (`sentSnap`) holds uncommitted entries or uncommitted queued prompts |
| `AckedOnlyDurable` | invariant | no client action is acknowledged by a link tick before its batch is durable on disk |
| `DurableMonotonic` | action | durable transcripts, next turn numbers, durable applied counters and acknowledgements never go backward, even across crashes |
| `NoOutBeforeFlush` | action | driver writes, staged link states and acknowledgements never advance while an unflushed batch holds uncommitted records |
| `Converges` | temporal | under fairness of pass steps, service restart after failure and driver answers, every action becomes durable, acknowledged and shown, and every turn settles |

Instances: per commit, `MCLoopPass.cfg` (one window, two actions, one crash, one failure, with `Converges`: 22,500 distinct states) and `MCLoopPassTwo.cfg` (two windows, one action each, one crash, one failure: 58,851 distinct states, 1 s); nightly, `MCLoopPassWide.cfg` (two windows, two crashes, one failure: 113,337 distinct states, 1 s) and `MCLoopPassThree.cfg` (one window, three actions, two crashes, one failure: 681,678 distinct states, 4 s).

Reversed witnesses (`witnesses/WLoop*.tla`), each rejected by TLC:

| Witness | The break | Rejected by |
|---|---|---|
| `WLoopReleaseBeforeFlush` | `Drivers::release` runs before `DurableStore::flush` | `PromptAtMostOnce` |
| `WLoopStateBeforeFlush` | `setState` stages the batch's state before `DurableStore::flush` | `LinkStateDurable` |
| `WLoopTickBeforeFlush` | links tick after `Apply` and before `DurableStore::flush` | `AckedOnlyDurable` |
| `WLoopNoHold` | the batch begins without `Drivers::hold` | `PromptAtMostOnce` |
| `WLoopReleaseOnFail` | a failed flush goes on to `Drivers::release` anyway | `DriverOnlyDurable` |
| `WLoopTickOnFail` | a failed flush loops to the next pass's tick instead of stopping | `AckedOnlyDurable` |
| `WLoopResetApplier` | reconnect initializes `Applier` to 0 instead of `disk.applied[c]` | `ExactlyOnce` |
| `WLoopNoTick` | `Tick` advances the pass without sending state or acknowledgements | `Converges` |
| `WLoopTurnReuse` | recovery resets the next turn number to 1 after cutting an open turn | `TurnsIncrease` |
| `WLoopCrashDropsDurable` | a crash wipes the durable store instead of recovering from disk | `DurableMonotonic` |
| `WLoopOutBeforeFlush` | `Hold` writes a send straight out while adding a record to the batch | `NoOutBeforeFlush` |

The binding: `tests/server/pass_walk.cpp` (`pass_walk <seed> <steps> [--fault release-before-flush | state-before-flush | tick-before-flush | no-hold | release-on-fail] <out.tla>`) drives `PassOrder` and `take_pass_step` (the same dispatch `Server::run` runs each pass through) over the real `DurableStore`, `Store`, `Journal` and `MemFs` (injecting `fail_at` before log append, between log append and sync, and inside compaction, and `MemFs::crash` with reverted, kept and random torn plans), `Hub`, `Drivers` and `Supervisor` over an in-memory `Drivers::Host` whose pipe writes are decoded by `driver::ServerReader`, and two windows over `FakeSender`/`FakeReceiver` and `Applier`. At every step it reopens a volatile-reverted copy of `MemFs` to record `disk` directly from durable bytes without shadow state. `LoopPassTrace.tla` checks five seeded walks per commit and rejects all five faulty pass configurations (`tlc_loop_pass_trace_faulty_*_rejected`).

## Running the checks

TLC needs Java 11 or newer and `tla2tools.jar`. The tests find the jar through `TLA2TOOLS_JAR`, and java through `JAVA` or `PATH`. Without `TLA2TOOLS_JAR` every `model` test fails and says what to set.

```sh
cmake -S . -B build
cmake --build build --target model_checks -j4
ctest --test-dir build -L unit
TLA2TOOLS_JAR=/path/to/tla2tools.jar ctest --test-dir build -L model -j "$(sysctl -n hw.ncpu)"
```

`-L model` matches two labels: `model` runs six instances (`MCWindowSprint`, `MCWindowEmpty`, `MCWindowNoSprint`, `MCWindow3Sprint`, `MCWindowAIs`, `MCWindowAIsEmpty`), the fifty-four witnesses, eleven code traces (with the sprint tab first: seeds 1 to 5 on three AIs, seed 6 on two AIs and seed 8 on one, each 1000 steps, and seed 7 with no AIs; without it: seed 9 on three AIs; with AIs coming and going: seed 10 with the sprint tab on three AIs, and seed 11 with neither), and the eleven faulty traces; for the overlay, `Overlay.cfg`, its twelve witnesses, three code traces and two faulty traces; for the client lock, `ClientLock.cfg`, its nine witnesses, three code traces and three faulty traces; `model_nightly` runs the three largest instances, `MCWindow`, `MCWindow3` and `MCWindowLong`. CI's per-commit job runs `-L '^model$'` and the nightly workflow `-L '^model_nightly$'`: every property is still checked on every commit, on the smaller instances. Each TLC run gets its own directory under `build/tests/model/tlc/<test>/`, a copy of the models, its own `java.io.tmpdir`, two workers (eight on every instance but `MCWindowEmpty`, which ctest counts as eight of its `-j` slots) and a 60 second cap (300 on the nightly instances); its log is `tlc.log` there, and a trace run leaves its `WindowTraceData.tla` beside it.

One check by hand:

```sh
cmake -DWORK=/tmp/tlc-window -DMODELS=$PWD/models -DMODULE=MCWindow -DCFG=MCWindow.cfg -DEXPECT=pass \
      -P tests/model/tlc.cmake
```

## Adding the next layer's model

1. Extend `Window.tla`, or write a new module that extends it, with the new variables and actions. Keep refused operations as steps that change no model state and record the operation and its result in `last`.
2. State each operation's guarantee as an action property on `last'`, and the state rules as invariants. Add the properties to every config.
3. Add a witness per property: a module in `witnesses/` that passes one broken action to `NextWithAll` (widen it with the new actions), and a config that checks only that property. Register it in `tests/model/CMakeLists.txt` with the property it must violate, then read its counterexample and confirm it fails for the reason intended.
4. Teach `trace_walk.cpp` the new operations and their arguments, and `WindowTrace.tla`'s `Step` the new record kinds. Keep a faulty subclass that the trace check rejects.
5. Keep each instance small enough that TLC finishes in seconds; bound growth with a state constraint, not with guards in the actions.
